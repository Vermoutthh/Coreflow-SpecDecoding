# 双卡并发回放初步检查（非容量结论）

2026-09-29 用 GPU 0、1 各启动一个真实权重的 vLLM V0 实例，分别服务
Plan 和 Task。两个实例使用相同的 Llama-3.1-8B target；开启 SD 时各自在
本卡装载 Llama-3.2-1B draft。配置为 `max_num_seqs=8`、前缀缓存开启、
eager 模式、单次最多生成 128 token。固定随机种子 2026，按泊松过程以
0.15 条 workflow/s 提交同样的 8 条 OWL-GAIA 完整 workflow，最多同时
放行 8 条。两组 manifest 完全一致，包含 194 次调用：Plan 73、Task 121。

| 配置 | 完成 workflow / 请求 | 完成率 (workflow/s) | 回放墙钟时间 | workflow P95 | Plan 实际调度 batch 均值 | Task 实际调度 batch 均值 |
|---|---:|---:|---:|---:|---:|---:|
| Plan K=0，Task K=0 | 8 / 194 | 0.0908 | 88.06 s | 84.96 s | 1.35 | 2.85 |
| Plan K=1，Task K=1 | 8 / 194 | 0.0947 | 84.45 s | 78.12 s | 1.31 | 2.72 |

K=1 时，从服务端指标采样得到的草稿 token 接受率约为 Plan 84.5%、
Task 82.0%。两组输出文字哈希在 194 次配对调用中有 186 次相同，
输出 token 数有 190 次相同；生成 token 总量也接近，但并非完全一致。
无 SD 组有 53/194 次输出达到 128-token 上限，因此这次输出长度分布
明显被截断；后续正式实验至少改用 256，并继续检查截断比例。

这是功能与指标链路检查，**不能把 0.0947 / 0.0908 当作稳定吞吐加速比**：
只有 8 条 workflow、一个到达率、每个配置只跑一次，整个测量还包含
逐渐提交和最后排空队列的阶段。这里的 P95 对 8 个样本实际接近最大值。
两卡固定为 Plan:Task = 1:1，也没有测试重新分配 GPU 的收益。

下一步应在相同模型与数据划分上增加 workflow 数，扫描多个到达率和
候选 K，并重复每个点；稳定容量须结合工作流完成率、延迟与排队走势判断。
上下文区间统计可解释请求差异，但不能把单次混合回放的区间延迟误称为
该区间独立实例的最大服务容量。
