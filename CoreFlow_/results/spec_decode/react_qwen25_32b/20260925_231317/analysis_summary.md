## 四、主要规律

### 4.1 接受率和加速比都随智能体及上下文变化，但变化幅度和方向不同

在固定 `k=5` 下，Plan 的接受率在 0-1024、1024-2048、2048-4096 区间依次为 56.5%、63.8%、63.5%；Task 依次为 55.0%、57.3%、54.1%。在 2048-4096 区间，两个智能体相差 9.4 个百分点。这说明智能体与上下文的组合确实可能影响草稿 token 的接受情况，而且接受率随上下文并不单调。Plan 在 4096-8192 区间只有 1 个样本，暂时不能讨论该区间的规律。

加速比同样随智能体和上下文变化，但并不只由接受率决定。例如 `k=5`、2048-4096 区间中，Plan 的接受率为 63.5%、加速比为 1.002x；Task 的接受率较低，为 54.1%，加速比却达到 1.053x。两组的平均输出分别为 36.0 和 98.5 token，输出长度可能解释部分差异。再看 Task 的 `k=1`：0-1024 和 4096-8192 的接受率分别为 81.2% 和 80.8%，但加速比从 1.201x 变为 0.982x。首 token 时间和解码时间的分解支持一种解释：长上下文增加的固定开销抵消了解码收益。

因此，应分别建立“接受行为”和“服务成本”模型，并在联合分配时组合。至少需要考虑：

1. 草稿 token 的接受情况；
2. 目标模型和草稿模型的预填充成本；
3. 每轮草稿与验证成本；
4. 预期输出长度。

### 4.2 只用一个平均接受率不够，应保留逐位置接受概率

`k=5` 时，所有请求在第 1 至第 5 个草稿位置上的接受概率依次约为：

| 草稿位置 j | 1 | 2 | 3 | 4 | 5 |
|---:|---:|---:|---:|---:|---:|
| 第 j 个 token 被接受的概率 | 76.4% | 63.1% | 53.8% | 46.5% | 41.0% |

规划智能体最后一个位置的接受概率约为 47.4%，执行智能体约为 39.3%。这正是不同智能体最优 `k` 可能不同的原因之一。

进一步固定上下文区间后，差别更集中在后部位置。`k=5`、上下文 2048-4096 时，Plan 第 1 个草稿位置的接受概率约为 78.4%，Task 为 75.2%；到第 5 个位置，分别为 53.9% 和 37.2%。这使 Plan 的每轮期望推进量约为 4.18 token，Task 约为 3.70 token。Plan 在该区间只有 26 个请求，分布于 8 条工作流，因此这个差异仍需要更多工作流复核。

检查本次 20 条工作流的原始提示发现，182 个 Plan 请求都被系统提示限制为 `Instruction/Input` 形式，307 个 Task 请求都被要求写较详细的 `Solution` 并以 `Next request` 结尾。Plan 的输出格式约束可能让草稿模型更容易预测后续 token，这是对智能体差异的一个可检验解释；当前结果无法把模板、任务语义和输出长度三者的作用完全区分开。

对每个“智能体—上下文区间—k”组合，应该记录逐位置接受概率 `q[a,b,k,j]`，而不是只记录平均接受率。一次验证轮的期望推进 token 数可以估计为：

```text
G(a,b,k) = 1 + Σ(j=1...k) q[a,b,k,j]
```

其中额外的 1 表示目标模型在发生拒绝或完成整段接受后仍能产生的目标 token。

### 4.3 上下文主要决定额外固定成本，输出长度决定该成本能否被摊薄

在 `k=1` 下：

- 总首 token 时间从 546.1 秒增加到 702.0 秒，上升 28.6%；
- 总解码时间从 1731.3 秒下降到 1357.1 秒，下降 21.6%；
- 两者合并后，端到端总时间下降 9.58%。

在 4096-8192 区间内，解码时间仍从 144.5 秒下降到 118.9 秒，但首 token 时间从 107.6 秒增加到 138.4 秒，最终端到端延迟反而略微变差。

固定 `k=5` 看单请求平均值，成本抵消关系更加直观：

| 分组 | 比 k=0 多出的首 token 时间 | 节省的解码时间 | 净节省时间 | 观察到的加速比 |
|---|---:|---:|---:|---:|
| Plan，2048-4096 | 约 0.500 秒 | 约 0.506 秒 | 约 0.006 秒 | 1.002x |
| Task，2048-4096 | 约 0.533 秒 | 约 0.853 秒 | 约 0.320 秒 | 1.053x |
| Task，4096-8192 | 约 0.980 秒 | 约 0.783 秒 | 约 -0.197 秒 | 0.976x |

可以把“推测是否值得启用”的初步判据写成：预期解码节省时间是否超过额外首 token 时间。上表只是单请求测量；进入 CoreFlow 后，还需要进一步计入批处理、实例显存和并发吞吐。

这说明推测解码存在一个典型的“固定成本—持续收益”权衡：

- 上下文越长，加载和处理草稿模型上下文的额外成本越高；
- 输出越长，后续解码节省越容易覆盖这部分固定成本。

### 4.4 输出长度是最强的收益预测特征之一

按照本次目标模型实际输出长度分组：

| 输出长度 | 请求数 | 最优 k | 最优加速比 |
|---|---:|---:|---:|
| 1-32 | 70 | 0 | 1.000x |
| 33-64 | 162 | 5 | 1.101x |
| 65-96 | 65 | 1 | 1.096x |
| 97-127 | 53 | 1 | 1.147x |
| 128 | 139 | 1 | 1.133x |

在本批实际输出不超过 32 token 的请求中，`k=0` 最快；较长输出组通常能获得推测收益。这是事后按实际输出长度分组的结果，不能在请求开始前直接知道该请求是否属于“32 token 以下”。此外，139 次输出恰好达到本次设置的 128 token 上限，属于截断观测，不能把这一组当作自然的“输出长度为 128”分布。

对 `k=1` 的单请求节省时间做一个简单线性拟合，可得到近似规律：

```text
节省时间（秒） ≈ 0.023
                 - 0.212 × 上下文长度（千 token）
                 + 1.000 × 输出长度（百 token）
                 + 0.048 × 是否为规划智能体
```

该简单模型在这 489 个样本上的决定系数约为 0.632，未做跨工作流验证，只用于描述本次观测到的方向，不能直接用于线上选择 `k`。

线上调度时不知道真实输出长度，但 CoreFlow 的 `RequestAnalyzer` 已经按照智能体和上下文区间统计了期望解码长度 `E_D`，因此可以直接使用历史期望输出长度，不需要预知本次请求的真实答案。需要注意，原始 DeepSeek 输出长度与本次 Qwen 输出长度的相关系数只有约 0.366，后续最好针对目标模型重新校准各类请求的输出长度分布。

### 4.5 当前最值得保留的候选是 k={0,1,3,5}

本次结果中，`k=2、4、6、7、8` 在主要分组上没有明显优势。但固定 `k` 的总延迟并不平滑：`k=3` 比 `k=2` 快，`k=5` 又比 `k=4` 快。当前每个 `k` 只测量了一次，无法判断这种起伏有多少来自测量波动、系统实现或真实的性能差异。下一轮重复实验可以先集中在：

```text
k ∈ {0, 1, 3, 5}
```

其中 `k=0` 表示不启用草稿模型，`k=1` 是本批数据最好的固定配置，`k=3` 和 `k=5` 用于检查看起来接近的候选。正式论文的大规模实验仍应保留完整 `k=0...8` 作为消融实验。

## 五、现有策略的收益

| 策略 | 选择方式 | 总端到端延迟（秒） | 加速比 | 相比固定 k=1 的额外收益 |
|---|---|---:|---:|---:|
| 最优固定策略 | 所有请求均为 k=1 | 2059.166 | 1.1060x | - |
| 按智能体选择 | Plan 使用 5，Task 使用 1 | 2053.800 | 1.1089x | 0.26% |
| 按上下文选择 | 1、5、1、0 | 2049.110 | **1.1114x** | **0.49%** |
| 智能体与上下文联合，样本内 | 8 个分组分别选 k | 2046.020 | 1.1131x | 0.64% |
| 智能体与上下文联合，留一工作流验证 | 只用其他工作流学习 k | 2059.210 | 1.1059x | 约 0% |
| 每条工作流单独选择的理想上界 | 每条工作流使用样本内最优 k | 2033.090 | 1.1202x | 1.28% |

按上下文选择的具体映射为：

```text
0-1024    -> k=1
1024-2048 -> k=5
2048-4096 -> k=1
4096-8192 -> k=0
```

该映射在这 20 个工作流的留一验证中保持不变，但相对固定 `k=1` 只额外提高 0.49%；基于工作流重采样得到的 95% 区间为 [-0.20%, 1.09%]。因此，这轮实验尚未证明按上下文动态选择 `k` 能稳定优于固定 `k=1`。

智能体与上下文的细粒度组合在样本内更好，但留一工作流后收益消失，说明当前 20 条工作流不足以可靠学习 8 个小分组，存在过拟合。

## 六、如何与 CoreFlow 联合建模

### 6.1 不建议直接训练“最优 k 分类器”

直接把每个请求最快的 `k` 当作标签会受到运行噪声影响，而且无法自然纳入 GPU 数量、批处理、显存和并发干扰。更合适的方法是分别建立“语义接受模型”和“硬件成本模型”，再由资源分配器联合求解。

### 6.2 语义接受模型

对智能体 `a`、上下文区间 `b`、推测长度 `k` 和位置 `j`，统计：

```text
q[a,b,k,j] = 第 j 个草稿 token 被目标模型接受的概率
G[a,b,k]   = 1 + Σ q[a,b,k,j]
```

样本不足时采用分层回退：

```text
智能体+上下文 -> 智能体 -> 全局
```

也可以使用 Beta-Binomial 或类似的平滑方法，避免 4096-8192 这种小样本区间产生极端估计。

### 6.3 单请求服务时间模型

设 `E_D[a,b]` 为 CoreFlow 已有的期望输出长度，则候选 `k` 下的请求时间可以近似写成：

```text
T_request[a,b,k]
  = T_target_prefill[b]
  + I(k>0) × T_draft_prefill[b]
  + E_D[a,b] / G[a,b,k] × L_round[a,b,k]
```

其中：

- `T_target_prefill`：目标模型预填充时间；
- `T_draft_prefill`：启用推测解码后草稿模型的额外预填充时间；
- `L_round`：一轮草稿生成加目标模型验证的时间；
- `G`：每轮期望推进的 token 数。

在批处理和并发条件下，应进一步把 `L_round` 写成批大小、平均上下文、最长上下文和 GPU 数量的函数。这样可以复用 CoreFlow 现有的注意力、MLP 和干扰延迟预测结构。

### 6.4 显存与资源约束

启用推测解码后，一个实例的显存需求变为：

```text
M_instance(k)
  = M_target
  + I(k>0) × M_draft
  + M_KV(batch, context)
  + M_runtime(k)
```

`k=0` 不需要加载草稿模型，而所有 `k>0` 通常都需要保留同一个草稿模型权重。因此，`k` 不仅改变延迟，还会改变可用 KV cache、最大批大小和可部署实例数，这部分必须进入资源分配约束。

### 6.5 与现有上下文分区动态规划的结合方式

当前 `InstanceOrchestrator` 已经在联合决定上下文区间边界和每个区间的实例数。最自然的扩展是把原来的吞吐缓存：

```text
(context_lower, context_upper) -> throughput
```

扩展为：

```text
(agent, context_lower, context_upper, k, gpu_count) -> throughput
```

动态规划的每条区间转移不再只选择分区边界，还同时选择该区间的 `k`。最终每个实例组包含：

```text
(智能体、上下文下界、上下文上界、k、实例数量、单实例吞吐)
```

工作流级的 `WorkflowAllocator` 可以保持原来的目标：不断给归一化吞吐最低的智能体增加实例，最大化整个多智能体工作流的瓶颈吞吐。

当前 vLLM 配置中的 `k` 是引擎级参数，并非简单的逐请求参数。因此，实际系统中应让不同上下文分区路由到配置不同 `k` 的实例池。CoreFlow 原本就会按上下文范围划分实例组，这一点与推测解码的联合分配天然匹配。

## 七、输出一致性说明

- 每个 `k` 都使用完全相同的 489 个请求，智能体和上下文元数据完全一致。
- 各推测实验与 `k=0` 单独比较时，有 463-465 个请求的输出 token 哈希完全相同，占 94.7%-95.1%。
- 每组有 477-480 个请求的输出长度相同，占 97.5%-98.2%；总输出 token 数的差异不超过 0.23%。
- 严格限制到所有 `k` 输出哈希都相同的 434 个请求后，结论不变：`k=1` 仍以 1.101x 排名第一，`k=5` 以 1.098x 紧随其后。

因此，输出差异没有造成当前性能排序，但投稿前仍应补做目标模型基线重复实验，区分这些差异来自张量并行和算子的数值非确定性，还是来自推测路径本身。后续小规模复核实验可以保存 token ID 或解码文本，以便检查差异是否具有语义影响。

## 八、当前结论与下一步

本次实验表明，在这组 Qwen2.5-32B/7B 模型和单请求运行配置下，固定 `k=1` 比 `k=0` 有稳定收益；较大的 `k` 未带来进一步的稳定提升。4096 token 以上的样本目前以 `k=0` 最快，但仅有 32 个请求，其中 Plan 只有 1 个。

对联合建模最重要的结论是：

1. 接受率用于描述语义可预测性；
2. 上下文长度决定草稿预填充和验证成本；
3. 预期输出长度决定额外成本能否被后续解码收益摊薄；
4. 智能体类型可以作为接受率和输出长度的先验；
5. GPU 数量、批大小、显存和实例数量必须与 `k` 一起进入 CoreFlow 的吞吐分配模型。

更关键的是，目前按上下文选择 `k` 比固定 `k=1` 只额外提高约 0.49%，还不能作为强有力的联合分配收益证据。下一步应增加工作流数量、重复测量关键 `k={0,1,3,5}`，并在不同批大小和并发负载下测量吞吐及显存占用。此外，本轮是原始提示的独立回放，不是让 32B 生成结果继续驱动后续智能体对话；正式的系统收益还需在真正连续执行的工作流或与之等价的回放设置下验证。这些数据才能回答：把推测解码放进 CoreFlow 的实例与 GPU 分配后，是否比固定 `k` 或完全不使用推测解码带来足够大的系统收益。
